【測試資料庫決策（使用者決議 2026-07-22）】
07_Testing_and_Acceptance_Plan_v1.0 §5 要求 API 整合測試使用「專用測試資料庫」，
但本機沒有 PostgreSQL／Docker。已詢問使用者，決議：
直接使用現有 Supabase 專案作為測試資料庫，直到專案完成為止。
為避免測試資料寫入正式資料庫，backend/tests/conftest.py 改為：
每個測試在一個 DB Connection 的 Transaction 內執行（SQLAlchemy 2.0
`join_transaction_mode="create_savepoint"`），測試中的所有 commit 只影響 SAVEPOINT，
測試結束後整個 Transaction rollback，實測確認 Supabase 各資料表測試後皆為 0 筆殘留。

【範圍補充說明】
需求追蹤矩陣 §4「開發階段對應」表原本沒有把「收藏」（模組 3.9）與「通知 API」
（模組 3.10 的會員端 GET/mark-read 部分）明確分配到任何一個階段（這是矩陣本身的
遺漏，不是規格文件間的衝突）。因為：
- 收藏功能與跟團清單同屬「會員個人清單管理」，且不依賴任何其他階段的 API；

  通知的 API，這些通知將無法被驗證與使用；
故將這兩者一併納入第 3 階段實作範圍，屬於補齊矩陣缺口，不是新增文件未規劃的功能。

     外部，選單和燈窗一起被關閉，「是」的 click 事件因此遺失、永遠無法
     真正登出。修正 handleClickOutside，偵測到點擊目標在 .modal-overlay
     內時直接略過。

【上傳圖片破圖問題 － 全站修復】
使用者回報頭像上傳後顯示破圖，追查後發現是全站性問題：後端上傳 API
回傳的是相對路徑（如 /uploads/avatar/2026/07/xxx.webp，掛載在後端 8000
port 根目錄），但前端所有圖片皆直接 <img src=...> 使用，未轉換為後端完整
網址，導致瀏覽器誤向前端自己的 origin（5173）請求該路徑而 404。
新增 frontend/src/api/client.js 的 resolveMediaUrl() 共用函式（絕對網址
直接放行，相對路徑補上後端 origin），並套用到全站約 19 處圖片顯示位置：
會員/團主頭像（ProfilePage x2、AvatarMenu、GroupLeaderProfilePage、
GroupLeaderListPage）、商品圖（ProductCard、ProductDetailPage、
ProductListPage、ProductFormPage、GroupBuyCreatePage、GroupBuyDetailPage、
FavoritesPage、FollowListPage、OrdersPage、OrderDetailPage）、活動圖
（ActivityCard、ActivityDetailPage、ActivityListPage、ActivityFormPage）。
已用 Playwright 實測頭像上傳全流程（含攔截網路請求確認圖片改用完整網址

新增功能：忘記密碼（規格外擴充）
--------------------------------------------------------------------------------
【後端】
- 新資料表 password_reset_token（migration 0008）：user_id（FK CASCADE）／
  token_hash／expires_at／consumed_at／created_at。token 只存 SHA-256 雜湊，
  資料庫外洩也反推不出可用連結；單次使用；預設 30 分鐘有效。

  找不到該 Email 時照樣回 201——若回 404，這支 API 會變成帳號列舉工具，
  任何人都能逐一測出哪些 Email 有註冊。前端提示語因此寫「若這個 Email 已註冊…」。
- GET /auth/password-reset-tokens/{token}：供前端在顯示表單前先確認連結有效。
- POST /auth/password-reset：以 token 設定新密碼。密碼更新與標記已使用在同一個
  Transaction，不會只完成一半。申請新連結會讓該會員先前未使用的連結立刻失效。
- 密碼規則抽成共用的 validate_password_strength()，註冊與重設共用同一套規則。
- config 新增 FRONTEND_BASE_URL（信件連結指向的前端網址）與 PASSWORD_RESET_*。

【信件美化（兩封都改）】
mailer 改為 multipart（HTML＋純文字雙版本），不支援 HTML 的信件軟體會退回純文字。
HTML 刻意使用 table 佈局與 inline style——Gmail、Outlook 會剝除 style 區塊與
現代 CSS 版面屬性，這是唯一可靠的做法。
- 共用外框：淡紫底、白色圓角卡片、品牌標頭（EchoGather＋寬字距紫色副標）、
  分隔線、頁尾提醒。
- 驗證碼信：驗證碼以淡紫底框襯托，34px 等寬字體、8px 字距，方便閱讀與複製。
- 重設密碼信：紫色大按鈕「重設我的密碼」，下方另附可複製的純文字連結
  （防按鈕被信件軟體阻擋），並標明有效期與單次使用。

【前端】
- ForgotPasswordPage 接上真實 API，寄出後顯示提示並進入 60 秒倒數
  （按鈕文字改「重新寄送」）。
- 新增 ResetPasswordPage（/reset-password?token=…）：進頁先驗證 token，
  無效／過期／已使用直接顯示失效畫面並提供「重新申請」入口；有效才顯示表單。
  兩個密碼欄各有眼睛切換，錯誤訊息沿用註冊頁那套。

【實測】申請重設→收到信→驗證 token→密碼太弱擋下→兩次不一致擋下→正確重設 204
→舊密碼登入 401→新密碼登入 200→同一 token 重用 400，全數正確。
不存在的 Email 照樣回 201 不洩漏；60 秒內重複申請回 429。

共用交易時鐘：本批兩次踩到的同一個坑
--------------------------------------------------------------------------------
created_at 的 server default 是 PostgreSQL 的 now()，它回傳「交易開始時間」
而不是敘述執行時間。影響：
- seed 在單一交易內建立所有資料 → 5 位團主、所有收藏的 created_at 完全相同，
  「依加入時間／收藏時間」排序退回次要鍵（隨機 UUID），等於沒作用。
  → seed 明確給遞增 created_at。
- 測試也跑在單一交易內（conftest 的 savepoint 機制）→ 同一測試建立的多筆收藏
  時間戳相同，排序測不出來。→ 測試以 _stamp_favorite_times() 明確指定時間，
  才測得到排序邏輯本身；順帶修掉原本碰巧靠 UUID 順序才通過的脆弱測試。
- 應用端限流計算混用兩個時鐘（差約 36 秒）→ 驗證碼與重設 token 都改為由
  應用端明確提供 created_at。

新增功能：團主申請三頁的即時更新
--------------------------------------------------------------------------------
【使用者裁決紀錄】
1. 做法 → 決議「輪詢＋回到頁面立即刷新」。

- 切回分頁或視窗重新取得焦點時立刻刷新，不等下一次輪詢
- 用 ref 保存 callback，避免每次 render 重設計時器

- 管理員申請列表：新申請自動出現

1. 靜默刷新：不清空資料、不切 loading，畫面不會每 30 秒閃一次

3. 測試：tests/test_group_leader_group_buy_stats_api.py（9 個，全數通過）
--------------------------------------------------------------------------------
涵蓋輪次編號、status 篩選後編號不變、輪次以團主為範圍、keyword 比對活動名稱、

（含跨商品同訂單只算一筆、未被訂購的商品仍出現、排除已取消）、非本人開團回 404。

【過程中抓到的 flaky 測試陷阱（值得記住）】
created_at 是 server_default=func.now()，而 PostgreSQL 的 now() 在同一交易內回傳
固定值（交易開始時間）。測試整包跑在一個交易裡，同一個測試建立的多筆紀錄 created_at
會一模一樣，凡是依時間排序的地方都會落到 id tie-break 上，變成 UUID 抽籤。
本批踩到兩次：
  1. 同一活動的兩輪開團 → 輪次編號隨機。「status 篩選後編號不變」那題失敗，
     另兩題只是剛好抽中。
  2. 商品訂購總覽的兩張訂單 → 明細「先喊先得」順序隨機。單獨跑該檔時通過，
     全套跑才失敗，是典型的偽偶發。
修法：測試明確指定不同的 created_at。factories.create_order_with_item 因此新增
選填 created_at 參數（docstring 已註明何時必須指定）。
與先前「寫死角色名今汐」「隨機名稱」屬同一類：測試不該依賴不受控的值。
生產環境每次操作都是獨立交易，created_at 不會相同，程式本身無此問題。

【全套測試才暴露的真實迴歸：管理員儀表板】
app/schemas/admin_dashboard.py 原本直接 re-export 團主端的 DashboardResponse
（一行 import，容易看漏）。團主儀表板依圖 20 新增必填的 current_group_buys 後，
管理員儀表板也被要求提供該欄位 → GET /admin/dashboard 回 pydantic ValidationError。
修法：admin_dashboard.py 改為自己定義 DashboardResponse（只有 cards），
管理員的「目前開團」本來就是獨立分頁端點 /admin/dashboard/current-group-buys。
DashboardCard 結構兩邊相同，仍共用。
教訓：跨模組 re-export 的 schema 在其中一端演進時會無聲波及另一端，
只跑相關測試檔看不出來，這類改動要跑全套。

3. 拆單（取消合併）功能
--------------------------------------------------------------------------------
流程：合併 → 會員在通知底下提出申請 → 團主核准（拆回）或拒絕（附原因）。
刻意做成與「取消訂單申請」同一套模式，會員端與團主端的心智模型一致。

【還原方式】目標訂單的明細扣掉各來源當初併進來的數量，扣到 0 的那筆刪除
（那是合併時新建的）；目標與來源的狀態／金額改回 order_merge 的快照。

【我自己定的邊界（使用者未指定，已在回報中說明）】
- 可拆狀態＝待確認／待付款／已付款，與可合併狀態一致；shipped 之後不可拆
- 同一張訂單同時只能有一筆待處理申請；被拒絕後可再提
- 二次合併只能從**最新**批次往回拆（先拆舊批次會把新批次的數量一起扣掉）
- 合併後團主若已收款再拆，帳目會回退到合併前——這正是團主有拒絕權的用途

【通知】合併通知含：哪幾張併到哪一張、被併掉訂單的**逐項商品明細**、金額說明、
「有問題請聯絡團主」、以及可提出取消合併。申請時通知團主，
核准／拒絕都通知會員。團主收到的訂單通知會導向團主端訂單頁——
notification_service 早就有「收件人不是下單者時視為團主」的判斷，直接沿用。

【循環匯入】notification_service 要判斷「這則通知還能不能按按鈕」，
但它不能 import order_service（order_service 會 import 它）。
把 UNMERGE_ALLOWED_STATUSES 移到 models/enums.py，兩邊都從那裡拿。

【團主訂單管理搜尋殘留（使用者回報）】
症狀：搜尋後就一直停在搜尋狀態，只能離開頁面再進來、F5、或手動清空搜尋框才能解除；

根因：該頁的 status／group_buy_id／has_pending_cancellation 是以網址為單一來源，

網址雖然乾淨了，元件狀態裡的搜尋條件卻還在。
修法：把 keyword 與 activity_id 也改成以網址為單一來源，與 status 同一套原則。
- 新增 updateParams() 統一寫網址參數（空值即移除，狀態與取消申請的互斥因此自動成立）
- 搜尋框輸入值（keywordInput）仍是元件狀態（否則每打一個字就查一次 API），
  但加一個 effect 跟著網址的 keyword 同步——點選單清空、瀏覽器上一頁時框內文字才會一起清掉
- 換任何篩選就回第一頁：原本停在第 3 頁改篩選，結果集可能不足 3 頁而顯示空清單
效果：點左側選單「訂單管理」→ 網址無 query → 所有篩選歸零 → 回到全部顯示。
副作用（正面）：搜尋結果現在可以分享網址、加書籤，上一頁／下一頁行為也正確了。

- admin/ProductListPage（商品管理）：activity_id／is_active／keyword
  （活動管理頁的「查看商品」本來就是靠 activity_id 帶進來，改成網址單一來源後
  「顯示全部商品」按鈕也只需清掉參數即可）

  group_buy_product.max_quantity          >  0    ← 不動

- 只有一個角色卻填 0        → 422 SINGLE_CHARACTER_QUANTITY_ZERO
- 多角色全部填 0            → 422 ALL_CHARACTER_QUANTITIES_ZERO

- 建立頁送出前把 0 濾掉了（filter(qty > 0)），0 會被後端 fallback 成商品上限

- 商品層級原本送「各角色最大值」，改送總和，與後端加總後的值一致。

**順帶補的缺口**：開團編輯頁原本只能改商品總上限，每角色上限是唯讀的，

7. 輸入框全站統一 ＋ 一個必須記住的特異性陷阱
--------------------------------------------------------------------------------
與下拉選單同樣的狀況：沒有全域 input 基準，沒被個別 class 指定樣式的輸入框
就是瀏覽器原生外觀（訂單篩選卡的「活動名稱」「團主名稱」就是）。
在 global.css 加 input／textarea 基準，與 select 同一套語彙。

**踩到的坑（使用者立刻發現 header 搜尋框變形）**：
第一版寫成
    input:not([type="checkbox"]):not([type="radio"]):not([type="file"]):not([type="range"])
每個 :not() 裡的屬性選擇器都計入特異性 → 這條是 (0,4,1)，比
`.search-input input` 的 (0,1,1) 還高，於是把膠囊搜尋框的 border:none／
background:none 蓋掉，登入頁 52px、團主搜尋 44px、個人資料 48px 這些自訂高度
也一併被壓成 40px。

改用 :where() 把整串 :not() 的特異性歸零，選擇器維持元素等級 (0,0,1)：
    input:where(:not([type="checkbox"]):not([type="radio"]):not([type="file"]):not([type="range"]))

select 那條沒出事是因為它本來就是單純的 `select`（0,0,1）。
以後要寫全域元素基準，一律用 :where() 包住條件，否則 class 規則反而蓋不掉它。

另外兩處「input 放在有邊框容器內」的寫法（.search-input input、
.glp-contact-row input）必須明確寫 height: auto——class 沒宣告 height 時，
全域的 height: 40px 仍會生效並撐開容器。

9. 管理員與一般用戶的 Email 命名空間分開（migration 0014）
--------------------------------------------------------------------------------
使用者需求：「管理員是和一般用戶分開的，所以管理員的信箱必須可以再註冊一般
用戶，而不要註冊時被告知已註冊」。

原本 uq_app_user_email_lower 是 LOWER(email) 全域唯一。改成兩個部分唯一索引：
  uq_app_user_email_lower_member  ON app_user (LOWER(email)) WHERE role <> 'admin'
  uq_app_user_email_lower_admin   ON app_user (LOWER(email)) WHERE role =  'admin'
同一 Email 最多「一般用戶 1 個 ＋ 管理員 1 個」，兩側各自仍唯一，
不會退化成完全沒有唯一性。

使用者問到「唯一性拿掉會不會沒有 primary key、要不要改成流水號」——
**不需要**。app_user 的主鍵一直是 UUID（UUIDPrimaryKeyMixin），只在系統內部
與外鍵使用、從不對外顯示，Email 只是唯一索引而非主鍵。

程式面：
  - user_repository.get_by_email 只找非管理員帳號（「這個 Email 能不能註冊」
    只看一般用戶那一側），新增 list_by_email 取同 Email 的所有帳號
  - auth_service.login 改為逐一比對密碼，由密碼決定登入哪個身分；
    list_by_email 讓管理員排前面，兩邊密碼相同時登入管理員，
    既有管理員帳號的行為不會因為別人用同 Email 註冊而改變

實測（API 層）：管理員 Email 請求驗證碼 201、註冊一般用戶 201、
管理員密碼登入得到 role=admin、會員密碼登入得到 role=member、
同 Email 再註冊第二個一般用戶正確回 409。

**踩到的坑**：alembic_version.version_num 是 varchar(32)，revision id 取太長
（0014_separate_admin_email_namespace，35 字）會在更新版本號時噴
StringDataRightTruncation——DDL 已經跑完卻整個 rollback。改成
0014_admin_email_namespace 才成功。以後 revision id 一律控制在 32 字以內。
