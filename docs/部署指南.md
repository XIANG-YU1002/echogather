## 步驟 0：先換掉所有金鑰（重要）

目前 `backend/.env` 裡的密碼與金鑰都曾在開發過程中傳遞過，上線前請全部重新產生。
**這一步必須由你本人操作**，我不會也不該代為執行。

| 要換的東西 | 到哪裡換 |
|---|---|
| Supabase 資料庫密碼 | Supabase 專案 → Settings → Database → Reset database password |
| `service_role` key | Supabase 專案 → Settings → API → 重新產生 |
| Gmail 應用程式密碼 | Google 帳戶 → 安全性 → 應用程式密碼（刪掉舊的、建新的） |

`service_role` key 可以繞過所有權限直接讀寫整個資料庫，外洩風險最高，務必更換。

換完後：
- 本機的 `backend/.env` 也要一起更新（否則本機開發會連不上）
- 新的值等一下要填進 Render，**不要寫進任何會進 git 的檔案**

## 常見狀況

**畫面出得來但顯示「無法載入資料」，Console 是 CORS 錯誤**
→ `CORS_ALLOWED_ORIGINS` 要填**全小寫**：`https://xiang-yu1002.github.io`

**這是上線時實際踩到的坑**，值得記住：瀏覽器送出 `Origin` 標頭時會把網域
**正規化成全小寫**，但 FastAPI 的 CORSMiddleware 是做字串精確比對，
所以填成含大寫的 `https://XIANG-YU1002.github.io` 就會被擋掉。

更陰險的是：用工具（curl／PowerShell）測試時，Origin 是自己帶的，帶大寫就會
「測起來正常」——**只有真的用瀏覽器打開才抓得到**。這也是為什麼驗收一定要
用真實瀏覽器，不能只打 API。

同理 `FRONTEND_BASE_URL` 的網域部分也要小寫，但後面的路徑 `/echogather`
要保留原本大小寫（網域不分大小寫，路徑分）。

**API 全部 404**
→ `VITE_API_BASE_URL` 結尾少了 `/api/v1`。

**重新整理後 404**
→ 前端 workflow 已經處理（把 `index.html` 複製成 `404.html`）。
若仍發生，確認 Actions 有跑完 `Add SPA fallback` 那一步。

**開發者工具看到 `/login`、`/orders` 回 404，但畫面正常**
→ 這是 GitHub Pages 的 SPA fallback 機制本身，不是故障。GitHub Pages 是純靜態
主機、沒有 rewrite 功能，所以前端路由的網址一定會回 404 狀態碼，只是內容被
換成 `404.html`（＝完整的 App），React Router 接手後畫面就正常了。
唯一實際影響是 SEO（搜尋引擎看到 404）。想拿到真正的 200，要換到支援
rewrite 的平台（例如 Cloudflare Pages 用 `_redirects` 寫 `/* /index.html 200`）。

**收不到驗證碼信**
→ 檢查 Render 的 `SMTP_PASSWORD` 是不是新的應用程式密碼、有沒有把空格去掉。
後端的行為是「先把驗證碼寫進資料庫、再寄信」，所以寄信失敗會回 502，
但驗證碼其實已經產生。
