# 上線部署指南

把 EchoGather 放到網路上，讓任何電腦／手機輸入網址就能使用。

> **狀態：已於 2026-07-31 完成上線**
> **主要網址 <https://www.echogather.workers.dev>**（Cloudflare，12 項實測全通過、
> Console 錯誤 0）
> 備援網址 <https://xiang-yu1002.github.io/echogather/>（GitHub Pages）
> 後端 <https://wuwagroup-api.onrender.com>

## 架構

| 部分 | 服務 | 費用 | 網址 |
|---|---|---|---|
| 前端（主要） | Cloudflare Workers | 免費 | `https://www.echogather.workers.dev` |
| 前端（備援） | GitHub Pages | 免費 | `https://xiang-yu1002.github.io/echogather/` |
| 後端（FastAPI） | Render 免費方案 | 免費 | `https://wuwagroup-api.onrender.com` |
| 資料庫＋圖片 | Supabase（現有） | 免費 | — |

兩份前端跑的是同一份程式碼，差別只在 `base` path（見 `frontend/vite.config.js`
的 `DEPLOY_BASE`）。Render 的 `CORS_ALLOWED_ORIGINS` 兩個網域都放行，可並存。

**為什麼主要用 Cloudflare**：GitHub Pages 是純靜態主機、沒有 rewrite，前端路由
（`/login`、`/orders`…）只能靠 404.html 接手，HTTP 狀態碼是 404，對 SEO 不利；
Cloudflare 的 `not_found_handling: "single-page-application"` 回的是真正的 200。
實測對照：

| 路徑 | Cloudflare | GitHub Pages |
|---|---|---|
| `/login` | **200** | 404 |
| `/orders` | **200** | 404 |

### 網址的組成（之後想改時要知道）

```
www . echogather . workers.dev
 ↑        ↑
 │        └─ Cloudflare 帳號子網域（Workers & Pages 頁面右側 Subdomain → Change）
 └─ Worker 名稱（wrangler.jsonc 的 name）
```
兩段都可改。取 `www` ＋ `echogather` 是為了讓網址讀起來像一般網站，
而不是「品牌.帳號名.workers.dev」。
改帳號子網域後 SSL 憑證要重新簽發，實測等了約 7 分鐘期間網址完全連不上，
屬正常現象。

前端的自動部署（`.github/workflows/deploy-frontend.yml`）在專案裡本來就有，
推上 main 就會自動建置並發布，且已處理 SPA 路由的 404 fallback。
所以要做的主要是**把後端部署起來，再把兩邊接上**。

- **Render 免費版 15 分鐘沒人使用會休眠**，下一個訪客要等 30～50 秒喚醒。

目前 `backend/.env` 裡的密碼與金鑰都曾在開發過程中傳遞過，上線前請全部重新產生。
**這一步必須由你本人操作**，我不會也不該代為執行。

| 要換的東西 | 到哪裡換 |
|---|---|
| Supabase 資料庫密碼 | Supabase 專案 → Settings → Database → Reset database password |

`service_role` key 可以繞過所有權限直接讀寫整個資料庫，外洩風險最高，務必更換。

換完後：
- 本機的 `backend/.env` 也要一起更新（否則本機開發會連不上）
- 新的值等一下要填進 Render，**不要寫進任何會進 git 的檔案**

## 步驟 5：確認資料庫是最新版本

從本機執行（Render 免費版沒有 Shell）：

```bash
cd c:\Users\user\Desktop\WuWaGroup\backend
venv\Scripts\alembic.exe upgrade head
```

目前應該已經在 `0014_admin_email_namespace`，會顯示沒有需要升級的項目。

### Migration 政策：forward-only（重要）

本專案**只做向前 migration**。正式環境永遠不執行 `alembic downgrade`。

各 migration 檔裡的 `downgrade()` 只保證能在**空資料庫**上跑，**有資料時不保證可用**。
已實測確認 `downgrade 0003 → 0002` 在資料庫存在多角色訂單時**必然失敗**：它要重建的
`uq_order_item_order_product` 唯一約束，與 0003 之後「同一訂單同一商品可有多筆不同
角色明細」的資料結構直接相斥。

因此每次執行 migration 一律照以下順序：

1. **先備份**：Supabase 後台 → Database → Backups，手動建立一次備份，
   或本機 `pg_dump` 存一份。確認備份完成才進行下一步。
2. **執行升級**：`venv\Scripts\alembic.exe upgrade head`。
3. **失敗處理**：**不要執行 `downgrade` 試圖回退**，改為還原步驟 1 的備份。
   先確認 `alembic_version` 的實際值，再決定還原範圍。

> 撰寫新 migration 時仍請照常實作 `downgrade()`（本機開發、重跑實驗會用到），
> 但不得據此宣稱「正式環境可安全回滾」。

### 怎麼確認部署真的生效

兩個前端各自部署，光看畫面分不出哪邊還停在舊版。每次建置會把 commit SHA
寫進 `index.html`：

```html
<meta name="build-version" content="fcf847554e6b..." />
```

在瀏覽器按 F12 查這個 meta，或：

```powershell
(Invoke-WebRequest "https://www.echogather.workers.dev/" -UseBasicParsing).Content `
  -match 'build-version" content="([^"]*)"' ; $Matches[1]
```

兩個網址的值一致且等於最新 commit，才代表真的都更新了。
**workflow 亮綠燈只代表指令沒報錯，不代表使用者拿到新版。**

### 手動部署 Cloudflare（備援，正常用不到）

在專案根目錄執行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\deploy-cloudflare.ps1
```

腳本會依序建置、**檢查產物路徑正確**、再部署。之所以包成腳本而不是要人記兩行
指令，是因為建置需要兩個環境變數，而漏掉不會報錯、只會安靜地部署出壞掉的版本：

- 少了 `DEPLOY_BASE=/` → 建置成 GitHub Pages 用的 `/echogather/`，
  但 Cloudflare 部署在根目錄，JS/CSS 全部 404（整站白畫面）
- 少了 `VITE_API_BASE_URL` → 前端退回 localhost，線上抓不到任何資料

腳本在部署前會檢查 `dist/index.html` 的資源路徑，不對就中止，不會傳上去。

> 註：`scripts\deploy-cloudflare.ps1` 必須存成 **UTF-8 with BOM**。
> PowerShell 5.1 讀取無 BOM 的 UTF-8 檔案時會把中文吃成亂碼，導致語法解析失敗。

### 自動部署踩過的坑（2026-07-31，連續失敗四次）

真正原因只有一個：**workflow 的 Node 版本是 20，但 wrangler 4.x 要求
Node >= 22**，被直接拒絕執行。`setup-node` 指定 `node-version: "22"` 就解決了。

之所以查了四輪，是因為錯誤訊息一直看不到：

1. `cloudflare/wrangler-action` 會**吞掉 wrangler 的輸出**，只回
   `The process ... failed with exit code 1`。改成直接 `run: npx wrangler deploy`
   之後，原始訊息才出現在 log 裡。
2. 就算出現了，那行 `Wrangler requires at least Node.js v22.0.0` 也在 log
   **中段**，被結尾的 `Error: Process completed with exit code 1` 蓋過去。
   只複製最後一兩行的話永遠看不到。

**教訓：CI 失敗時要看完整 log，不能只看結尾的摘要行。**
一路上還順手補了兩個本來就該指定的設定（`account_id`、wrangler 版本），
它們不是失敗主因，但留著能讓 CI 行為明確。

## 常見狀況

**畫面出得來但顯示「無法載入資料」，Console 是 CORS 錯誤**
→ `CORS_ALLOWED_ORIGINS` 要填**全小寫**：`https://xiang-yu1002.github.io`

**這是上線時實際踩到的坑**，值得記住：瀏覽器送出 `Origin` 標頭時會把網域
**正規化成全小寫**，但 FastAPI 的 CORSMiddleware 是做字串精確比對，
所以填成含大寫的 `https://XIANG-YU1002.github.io` 就會被擋掉。

更陰險的是：用工具（curl／PowerShell）測試時，Origin 是自己帶的，帶大寫就會
「測起來正常」——**只有真的用瀏覽器打開才抓得到**。這也是為什麼驗收一定要
用真實瀏覽器，不能只打 API。

同理 `FRONTEND_BASE_URL` 的網域部分也要小寫，但後面的路徑 `/echogather`
要保留原本大小寫（網域不分大小寫，路徑分）。

**API 全部 404**
→ `VITE_API_BASE_URL` 結尾少了 `/api/v1`。

**重新整理後 404**
→ 前端 workflow 已經處理（把 `index.html` 複製成 `404.html`）。
若仍發生，確認 Actions 有跑完 `Add SPA fallback` 那一步。

**開發者工具看到 `/login`、`/orders` 回 404，但畫面正常**
→ 這是 GitHub Pages 的 SPA fallback 機制本身，不是故障。GitHub Pages 是純靜態
主機、沒有 rewrite 功能，所以前端路由的網址一定會回 404 狀態碼，只是內容被
換成 `404.html`（＝完整的 App），React Router 接手後畫面就正常了。
唯一實際影響是 SEO（搜尋引擎看到 404）。想拿到真正的 200，要換到支援
rewrite 的平台（例如 Cloudflare Pages 用 `_redirects` 寫 `/* /index.html 200`）。

**收不到驗證碼信**
→ 檢查 Render 的 `SMTP_PASSWORD` 是不是新的應用程式密碼、有沒有把空格去掉。
後端的行為是「先把驗證碼寫進資料庫、再寄信」，所以寄信失敗會回 502，
但驗證碼其實已經產生。
