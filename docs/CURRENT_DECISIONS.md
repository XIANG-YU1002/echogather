## 2. 專案定位與第一版範圍

### 2.1 平台定位

EchoGather 是《鳴潮》官方周邊的**開團資訊整合與跟團管理平台**，不是完整電商平台。
平台不處理實際金流、不代收款、不驗證付款、不計算運費。

### 2.2 主要角色

| 角色 | 定位 |
|---|---|
| Visitor | 未登入使用者，只能瀏覽公開內容 |
| Member | 已註冊並登入的使用者 |
| Group Leader | 具備團主資格的會員，可開團並管理自己開團的訂單 |
| Admin | 獨立管理用途帳號，只使用管理後台，管理活動、商品、團主申請與平台公告 |

### 2.3 第一版明確不提供

- 站內付款、自動對帳、退款
- 二補金額管理、國際運費計算、國內物流費計算、物流單號、宅配追蹤
- 站內聊天、私訊
- 評價、星等
- 盲盒拆分、熱度定價
- 商品規格變體、多遊戲支援、行動 App
- Refresh Token
- 會員帳號停用、團主資格停用、公告停用
- 會員自行刪除通知
- 開團草稿、排程發布、審核後發布
- 已結單開團重新開啟

## 3. 帳號、認證與角色

### 3.1 角色定位

- **Visitor** 可瀏覽公開活動、商品、角色、開團比較、公開團規、已完成資料的團主
  公開頁與團主選擇公開的公告。Visitor 不可收藏、不可使用購物車、不可下單、
  不可查看通知、不可申請團主、不可進入團主或管理員後台。
- **Member** 除 Visitor 功能外，可管理個人資料與私人聯絡方式、收藏商品、
  使用購物車、送出訂單、查看自己的訂單、提出取消申請、查看與標記通知、
  申請團主資格。
- **Group Leader 是「具備團主資格的會員」**，不是獨立帳號、不是獨立角色值。
  團主資格由是否具有團主資料判定。
- **Admin 是獨立管理用途帳號，只使用管理後台。**
  **Admin 帳號不得使用收藏、購物車、下單、團主申請與團主後台。**
  同一真人若需要會員或團主功能，必須使用另外的一般會員帳號。

### 3.2 註冊與登入

- 註冊必須提供：Email、密碼、密碼確認、暱稱、以及 Facebook／Discord／LINE
  至少一項私人聯絡方式。頭像為選填，未上傳時使用系統預設頭像。
- 註冊必須通過 Email 驗證碼：6 位數、雜湊儲存、10 分鐘有效、單次使用；
  同一 Email 兩次寄送間隔至少 60 秒、每日上限 10 次、驗證碼錯誤 5 次後失效；
  已註冊的 Email 不予寄送。
- 密碼長度 8～72 字元，至少包含一個英文字母與一個數字。後端只保存安全雜湊。
- **註冊成功後自動登入並導向首頁。**
- **僅在自動登入失敗時，才導向登入頁並提示使用者登入。**
  註冊時選擇的頭像於自動登入後上傳套用；頭像上傳失敗不影響帳號已建立的事實。
- 登入失敗一律顯示統一訊息，不得透露 Email 是否存在。
- Access Token 有效 8 小時，前端存於 sessionStorage，不提供 Refresh Token，
  不提供後端登出端點；登出由前端清除 Token 與登入狀態完成。
- 會員自受保護頁面被導向登入時，登入成功後返回原本要前往的頁面；
  下單、審核、刪除與狀態變更等敏感操作不自動重送。

### 3.3 Email 與私人聯絡方式

- Email 儲存前 Trim、正規化為小寫、大小寫不敏感且不可重複。
- **第一版會員不可自行修改 Email。**
- 會員私人聯絡方式在註冊及每次更新後，**至少保留一項**；三項全為空不允許保存。
- 私人聯絡方式：本人可查看；下單時保存至訂單聯絡快照，該訂單所屬團主可查看快照；
  公開 API 與公開頁一律不得回傳；不自動成為團主公開聯絡資料。
- 會員修改個人聯絡資料時，不修改既有訂單的聯絡快照。

## 4. 首頁、導覽與搜尋

- **Header 不提供獨立的活動入口與商品入口。**
- **活動主要從首頁瀏覽。** 首頁分「目前活動」與「已結束活動」兩區，
  各區依活動建立時間由新到舊排列。
- **商品從活動頁或搜尋進入。**
- 首頁不提供活動分類篩選。
- **全站搜尋只搜尋商品與角色，不搜尋活動。** 搜尋不涵蓋會員、團主名稱、訂單、
  公告、團規與聯絡方式。
- 搜尋文字 Trim 後不可為空；支援部分文字比對。
- 搜尋結果於同一頁分區顯示，各區有自己的總筆數與分頁，不使用 Tabs。
- 公開搜尋與活動商品列表只顯示上架商品。
- **使用者介面正式名稱為「購物車」。** 全站前台文字一律使用「購物車」。
- **內部 `follow_list` 的 API、Model、Service 與資料表命名暫時保留，
  不因 UI 用語而重命名。** 此為已確認狀態，不是待修問題。

## 5. 活動、商品與角色

### 5.1 活動

- 活動是管理員建立的**獨立資料**，代表實際官方活動，**不是固定分類**。
  管理員每新增一筆活動，首頁即新增一張活動卡片。
- 活動狀態只有兩種：
  - `open`：顯示於「目前活動」區，可建立新開團。
  - `ended`：顯示於「已結束活動」區，可繼續瀏覽活動、商品、歷史開團與訂單，
    不可建立新開團。
- 管理員可結束活動，也可重新開啟。重新開啟後活動回到「目前活動」區並可再次
  建立新開團；已提前結單的開團不因此重新開啟。
- 活動名稱 Trim 後不可為空。第一版不要求活動名稱全站唯一。
- 第一版活動不保存開始日期與結束日期。

### 5.2 商品與角色

- 每項商品只能屬於一項活動，可關聯零至多名角色，可具有一張主圖與多張額外圖片。
- 商品至少需要：所屬活動、商品名稱、主要圖片。
- 同一活動內不可建立兩筆完全相同的商品名稱；不同款式須明確寫入名稱。
- 角色是全站共用資料，可跨活動關聯商品，不隸屬單一活動。第一版角色只保存名稱。
- 角色名稱 Trim 後不可為空、大小寫不敏感且不可重複；同一商品不可重複關聯同一角色。
- 管理員在商品表單新增角色時，**當下即建立角色**。
- 已有商品關聯的角色不可刪除，須先移除全部商品關聯；此限制由後端強制。
- 第一版不提供獨立角色管理頁，亦不提供角色改名功能。

### 5.3 商品上下架與收藏

- 商品以上架／下架狀態控制，不刪除。
- 上架商品顯示於公開活動頁與公開搜尋，可加入有效開團與購物車。
- 下架商品不顯示於公開商品列表與搜尋；歷史開團與訂單資料保留；
  既有失效購物車不自動刪除；不可建立新的有效下單內容。管理員可重新上架。
- 第一版只收藏商品，不收藏活動、開團、團主或公告。
- 同一會員對同一商品最多一筆收藏；重複收藏不建立重複資料；
  重複取消收藏視為成功。
- 商品下架後收藏關聯保留、收藏頁仍顯示該商品並明確標示「商品已下架」，
  且不可從收藏頁建立無效的下單內容。

### 5.4 幣別

- **團主售價與訂單金額固定使用 TWD**，不提供幣別切換或匯率換算。
- 後端金額使用 Decimal，資料庫使用固定小數位數值型別，API 以字串傳輸金額，
  不使用浮點數計算。
- **商品「官方價格」的可用幣別範圍尚未確認，見第 17 節。**

## 6. 購物車

- **一名會員同時最多一個購物車。**
- **一個購物車只能屬於一個開團**，因此一個購物車自然只包含一名團主、一項活動、
  一套付款方式、一套團規與一項主要聯絡方式。
- **同一開團的同一商品、同一角色再次加入時，數量累加**，不建立第二筆項目。
- **同一商品的不同角色分開保存為獨立項目。**
- 同一開團的新商品可直接加入現有購物車。
- 目前購物車屬於其他開團時不可混合。前端須詢問是否替換；確認替換後，
  後端在單一交易內驗證、刪除舊購物車、建立新購物車與項目；
  新購物車建立失敗時舊購物車不得遺失。
- 項目數量必須大於 0；修改數量使用絕對數量，不是增加量。
- **購物車不占用接單上限、不保留商品、不建立訂單順位**，也不保證稍後仍有相同
  剩餘數量。
- 商品或開團失效時（開團提前結單、開團截止、活動結束、商品下架、剩餘數量不足），
  **既有購物車不自動刪除**。會員仍可查看失效原因、修改數量、移除單項、清空購物車，
  但不可正式送出。
- 刪除最後一項時，同時刪除空的購物車。
- 多角色商品加入購物車時必須選擇角色；單一角色商品自動帶入該角色。
- 團主能否購買自己的開團尚未確認，見第 17 節。

## 7. 訂單

### 7.1 建立訂單

- **會員每次正式送出購物車，一律先建立一筆全新、完全獨立的訂單。**
- **不得在下單時自動合併到舊訂單。** 同一會員對同一開團再次送出時，
  建立第二張訂單並排在第一張之後，只能使用該次送出當下仍可接受的數量。
- **每筆訂單具備獨立的訂單編號、送出時間、狀態與資料快照。**
- 送出前會員必須明確勾選同意本次團規；未勾選不得建立訂單。
- 正式訂單只能從會員目前的購物車建立。前端不得決定或提交單價、小計、商品總額、
  商品名稱、商品圖片、團主名稱、活動名稱或任何快照內容，一律由後端重新查詢與計算。
- 建立為全有或全無：所有商品皆成功才建立完整訂單；任一項失敗不建立部分訂單，
  且保留完整購物車。成功後才清空購物車。
- 訂單快照至少保存下單當時的：團主名稱、活動名稱、付款方式、付款方式說明、
  是否二補、是否包含滿贈、團規、團主主要聯絡方式、會員私人聯絡方式、
  商品名稱、商品主圖、所選角色、單價、數量、小計。
  後續任何資料變更不得改寫既有訂單快照。

### 7.2 數量與順位

- **數量依成功送出順序分配。** 團主端的訂單處理順序以訂單建立時間排序，
  建立時間相同時以識別碼作為穩定排序。
- 順位使用伺服器建立時間，不使用使用者裝置時間。
- 已占用數量為所有未取消、未拒絕、未被合併的訂單明細數量總和；已完成訂單
  **仍計入**已占用數量。訂單取消或被拒絕時釋放占用數量。
- 可接受數量＝接單上限－已占用數量，且不小於 0。
- 有角色的商品，占用量與可接受數量以（開團商品, 所選角色）為單位計算。
- 兩名會員同時送出時，後端鎖定相關開團商品，依交易實際成功順序建立訂單；
  後取得鎖定者必須以更新後的剩餘數量重新驗證；數量不足者整筆失敗並保留購物車。

### 7.3 金額

- **商品總額不包含二補、國際運費、國內運費、超商或宅配費及其他團主後續費用。**
- 畫面一律顯示「商品總額」，不得只顯示「總額」。

### 7.4 訂單狀態流程

| 目前狀態 | 操作 | 下一狀態 | 執行者 |
|---|---|---|---|
| 待確認 | 確認訂單 | 待付款 | 團主 |
| 待確認 | 拒絕訂單 | 已拒絕 | 團主 |
| 待付款 | 標記已付款 | 已付款 | 團主 |
| 已付款 | 標記已出貨 | 已出貨 | 團主 |
| 已出貨 | 完成訂單 | 已完成 | 團主 |
| 待確認／待付款／已付款 | 核准取消申請 | 已取消 | 團主 |

- 未列出的直接轉換全部禁止。
- 拒絕原因必填、Trim 後不可為空、拒絕後不可修改；被拒絕的訂單不可恢復、
  不進入付款流程、不占用數量，但保留歷史資料。
- 已完成訂單保留數量占用，且不可再提出取消申請。
- 前端顯示可操作但後端發現狀態已變更時，不執行操作、回傳目前狀態，
  由前端重新載入。

### 7.5 取消申請

- 會員可於待確認、待付款、已付款狀態提出取消申請。
- 已出貨、已完成、已取消、已拒絕的訂單不可提出取消申請。
- 取消原因為選填。
- 同一訂單同時最多一筆待處理取消申請。
- 建立取消申請時訂單狀態保持原狀、不立即釋放數量；團主訂單列表標示有待處理申請。
- 團主核准前須重新確認訂單目前仍可取消；核准後訂單成為已取消、釋放占用數量、
  建立會員通知，且不可再次提出取消申請。
- 團主拒絕後訂單維持原狀態；會員在訂單仍為可取消狀態且無其他待處理申請時，
  可再次提出新申請。每次申請保留獨立歷史紀錄。
- **團主拒絕會員的取消訂單申請時，拒絕回覆為選填；未填寫回覆不影響拒絕成立。**
  此規則不影響取消合併／拆單申請的拒絕理由規則（見第 7.6 節，該處拒絕必須填寫原因）。

### 7.6 訂單合併與拆單

**合併（團主手動操作，非系統自動）**

- **團主可手動合併符合條件的訂單。** 條件為：同一開團、同一會員、狀態為待確認／
  待付款／已付款、且無待處理取消申請。
- 保留哪一張訂單（最舊或最新）由團主選擇。兩張訂單的建立時間都不改寫，
  以維持先喊先得的順位。
- 同商品**同角色**的數量相加；不同角色維持獨立明細。
- 合併後狀態：全部已付款則維持已付款，否則為待付款。不新增「部分已付款」狀態；
  已收金額另行記錄，待收金額為總額減已收。
- 來源訂單標記為「已合併」，其明細與金額保留不動。已合併的來源訂單在會員端與
  團主端的列表、詳情與統計一律不顯示，資料完整保留以供還原。
- 合併後通知會員：哪幾張併到哪一張、被併訂單的商品明細、金額說明與聯絡團主提示。

**拆單（取消合併）**

- **由會員提出申請，團主審核。**
- 團主可拒絕，但**必須填寫原因**；拒絕後訂單維持合併後的狀態，會員可再次申請。
- 核准後還原成合併前各自的狀態與金額（含已收金額），來源訂單重新顯示。
- 訂單進入已出貨之後不可再拆。
- 同一張訂單同時只能有一筆待處理的拆單申請。
- 二次合併只能從最新批次往回拆。
- 核准與拒絕都通知會員。

## 8. 付款方式

**第一版每一個開團只能設定一種付款方式：**

- 匯款
- 取貨付款
- 其他

規則：

1. **選擇「其他」時必須填寫付款方式說明。**
2. **會員送出訂單時不需要再次選擇付款方式**；訂單保存該開團的付款方式快照。
3. 一筆開團只保存一種付款方式，付款方式為開團層級設定。
4. **複數付款方式，以及讓會員自行選擇付款方式，延後至未來版本。**

> **實作差異標記：** 目前程式碼、資料庫列舉型別與一項既有測試僅支援「匯款」與
> 「取貨付款」兩種，並主動拒絕「其他」。此為**尚待同步的實作差異**，不是本節
> 規格的例外。詳見第 16 節。

## 9. 團主申請與團主資料

### 9.1 申請與審核

- 會員可申請團主資格的條件為：目前沒有團主資料，且目前沒有待審核申請。
  已具團主資料的會員不可再次申請。
- 同一會員同時最多一筆待審核申請。歷史申請保留。
- 申請被拒絕後不設等待期間，可再次申請；新申請建立新紀錄，舊申請結果保留。
- 申請原因為**選填**，上限 1000 字，僅供管理員審核參考；未填寫不構成拒絕理由，
  系統也不因此阻擋送出。
- 申請頁必須顯示平台規範全文，會員須勾選「我已確認並會遵守平台規範」後才能送出；
  未勾選時送出按鈕停用。
- 管理員可通過或拒絕申請。第一版不要求審核備註。已審核的申請不可再次審核。
- 通過時於單一交易內：確認申請仍為待審核、確認會員尚無團主資料、更新申請為通過、
  建立一筆尚未完成的團主資料、建立申請結果通知。
- 拒絕時更新申請為拒絕、保存審核時間、建立申請結果通知，且不建立團主資料。

### 9.2 團主公開資料完成條件

- 團主資料完成條件為：**已設定公開名稱，且至少一項公開聯絡方式不為空。**
- 資料未完成時：不公開團主頁、不可建立開團、不可發布公告；
  可進入團主資料設定頁並修改介紹、預設團規與公開聯絡方式。

### 9.3 公開名稱與公開聯絡方式

- 公開名稱 Trim 後不可為空、大小寫不敏感且不可與其他團主重複。
- **公開名稱第一次設定成功後不可修改**，團主本人與管理員皆不可修改。
- 名稱完成後仍可修改團主介紹、預設團規與三項公開聯絡方式；每次更新後仍須
  至少保留一項公開聯絡方式。
- 團主公開聯絡資料由團主主動填寫，不得從會員私人聯絡方式自動複製。
- Facebook 一律必須是個人頁連結，不接受只填帳號名稱。此規則於會員聯絡欄位、
  團主公開聯絡方式與開團主要聯絡方式三處一致。

### 9.4 團主公開頁與功能限制

- 只有完成公開資料的團主才有公開頁。公開頁不得回傳會員私人聯絡方式。
- 公開頁可顯示：頭像、團主名稱、團主介紹、公開聯絡方式、成為團主時間、開團數、
  完成訂單數、預設團規、目前開團、公開的團主整體公告。
- 第一版公開頁不顯示評價或星等。
- 預設團規顯示於公開頁並可用於預填新開團；修改預設團規只影響未來預填內容，
  不修改既有開團團規與既有訂單的團規快照。

## 10. 開團管理

### 10.1 建立開團

- 建立開團必須符合：已登入、具備團主資料、且團主公開資料已完成。
- 建立流程先選擇一項狀態為 `open` 的活動；已結束活動不可建立新開團。
- 一筆開團至少包含一項商品；商品不得重複；所有商品必須屬於所選活動；
  所有商品在建立當下必須為上架狀態。
- **同一團主對同一活動同時只能有一個進行中的開團**，結單後可再開新的一輪。
- 每個開團商品必須設定團主售價與接單上限。
- 有角色的商品，每個角色各有自己的接單上限；商品層級上限為各角色上限的總和。
  每角色上限允許 0，代表不接該角色的單。以下三種情況拒絕：商品只有一個角色
  而該角色填 0；多角色但全部填 0；該角色上限低於已占用數量。
- 收單期限必填，且必須晚於建立當下時間。後端保存 UTC，前端以 Asia/Taipei 顯示。
- 每筆開團必須提供完整團規、主要聯絡平台與主要聯絡內容；團規與聯絡內容
  Trim 後不可為空。
- **開團的主要聯絡方式必須取自團主資料已設定的公開聯絡方式**，不在開團另外輸入。
  團主資料未設定該平台時拒絕並提示先於團主資料填寫；只切換平台時，
  系統自動採用團主資料該平台的值。
- 「是否包含滿贈」只允許在活動支援滿贈時設定。
- 「是否需要二補」只提供資訊，平台不計算、不收取、不追蹤二補付款。
- 開團建立後立即成為進行中狀態，第一版不提供草稿、排程發布與審核後發布。

### 10.2 團主儀表板與我的開團

- **團主儀表板依活動分組顯示目前進行中的開團。此功能已完成。**
- **介面文字統一：「依活動分類」一律改稱「依活動分組」。**
- **介面文字統一：「管理開團」一律改稱「開團設定」。**
- **「我的開團」包含全部、進行中與已結單的完整開團紀錄，並具備搜尋、排序、
  篩選與分頁。此功能已完成。**

### 10.3 編輯與結單

- 判斷開團是否已有正式訂單時，只要存在任何訂單紀錄即視為已有正式訂單；
  該訂單之後成為已取消或已拒絕，也不恢復為「從未有訂單」。
- **沒有任何正式訂單時可修改全部內容**：活動、商品集合、各商品售價、
  各商品接單上限、付款方式、付款方式說明、是否二補、是否包含滿贈、收單期限、
  團規、主要聯絡方式。修改後仍須重新符合所有建立規則。
- **已有正式訂單後只可修改**：收單期限、主要聯絡平台、主要聯絡內容、
  各商品接單上限（含每角色上限）。
- **已有正式訂單後不可修改**：活動、商品集合、商品售價、付款方式、
  付款方式說明、是否二補、是否包含滿贈、團規。
- **接單上限不得低於已占用數量**，否則拒絕修改。此規則同時適用於商品層級與
  每角色層級。
- 修改後的截止時間不得早於目前時間。已有訂單後可延長或縮短期限。
  要立即停止收單使用「提前結單」，不是把期限改到過去。
- 團主可提前結單。結單後不接受新的購物車項目與新訂單，既有訂單繼續處理，
  歷史資料仍可查看，**第一版不可重新開啟**。
- 開團的實際可用狀態由系統計算，不直接保存，且須能清楚回傳主要不可用原因。

## 12. 公告與通知

### 12.1 團主公告

- 發布團主公告需要具備團主資料且公開資料已完成。
- 團主公告有兩種通知範圍：
  - **團主整體公告**：通知曾加入該團主、且目前在該團主名下至少有一筆未完成訂單
    的會員。
  - **特定開團公告**：通知指定開團中至少有一筆未完成訂單的會員。指定開團必須
    屬於該團主。
- 通知對象的訂單狀態包含待確認、待付款、已付款、已出貨；排除已完成、已取消、
  已拒絕、已合併。
- 同一會員即使有多張訂單、多項商品或多次加喊，同一公告仍只建立一則通知。
- 公告標題與內容必填、Trim 後不可為空、使用純文字、保留換行、不執行 HTML。
- 公告建立後立即發布；第一版不提供草稿、排程發布與自動到期。

### 12.2 公開與非公開

- 團主可選擇公告是否公開。公開只影響公開頁顯示，不改變通知對象。
- 團主整體公開公告顯示於團主公開頁；特定開團公開公告顯示於該開團公開頁。
- 通知對象為零時：**公開公告允許發布；非公開公告阻止發布。**
  將既有零收件人的公開公告改為非公開時，適用相同規則。

### 12.3 修改與刪除

- 團主可修改自己公告的標題、內容與是否公開；不可修改公告範圍、指定開團、
  發布者與發布時間。
- **修改公告時同步更新該公告已建立的通知標題與內容**，不重新建立通知、
  不重設通知已讀狀態、不改變原收件人集合。
- **刪除公告時一併刪除該公告建立的通知**，不影響訂單通知、申請結果通知
  與其他公告的通知。
- 第一版不提供公告停用。

### 12.4 平台公告

- 只有管理員可建立平台公告，通知所有已註冊會員帳號，同一公告對同一會員
  只建立一則通知。
- 平台公告不建立獨立公開列表與獨立公開詳情頁，主要顯示於會員通知中心。
- 管理員可修改與刪除平台公告；修改同步更新既有通知且不重設已讀狀態；
  刪除只刪除該公告與其通知。

### 12.5 通知

- 通知只對應一個來源：訂單、公告或團主申請。
- 新通知為未讀；標記已讀後保存第一次標記時間，重複標記不更新該時間。
- 會員可查看通知列表、篩選已讀或未讀、標記單筆已讀、全部標記已讀、
  點擊前往相關頁面。
- **會員不可一般性刪除通知。** 唯一例外為公告被刪除時，系統一併刪除該公告
  建立的通知。

### 12.6 公告管理頁

- **公告管理頁是團主的全域公告管理中心**，可同時管理團主整體公告與特定開團公告。
- 現有左側導覽與公告列表設計沒有問題。
- **不要求公告管理頁顯示「商品訂購總覽／開團設定／團購公告」三個頁籤。**
- 自特定開團帶入開團篩選時，顯示目前篩選的開團名稱或提供返回該團入口，
  **屬可選 UX 改善，不是第一版必要修改，也不是目前的功能缺陷。**

## 14. 測試與資料庫環境

1. **自動化測試必須使用獨立測試資料庫、獨立 Supabase 專案或獨立 PostgreSQL
   Schema。**
2. **不得對主要開發資料庫或正式資料庫執行會建立、修改或刪除資料的測試。**
3. 正式資料庫結構變更必須透過 Alembic Migration，不得以手動修改正式資料庫取代
   Migration。
4. Migration 採 forward-only 政策：正式環境不執行 downgrade，回退一律還原備份，
   修正錯誤以新增 forward migration 進行。
5. 任何具外部副作用的管道（寄信、檔案上傳）在測試中必須被攔截，
   測試不得對真實外部服務產生副作用；新增此類管道時，測試防護必須同步覆蓋。
6. 測試資料不得使用真實個人資料。

> **實作差異標記：** 現有 `backend/tests/conftest.py` 仍連接主要 Supabase 專案，
> 以每個測試在交易內執行並回滾的方式規避殘留。此為**待修正的工程問題**，
> 詳見第 16 節。
