# 第 1 章 文件目的與使用指引

## 1.1 文件定位

本文件是 EchoGather 第一版**產品規格的單一權威入口**：

- 專案定位與版本範圍、產品與業務規則、使用者角色與權限、功能流程與邊界條件、
  UI 主要導覽與畫面狀態規則、Database 與 API 的整體設計、測試範圍與驗收標準、
  延後功能、已知規格與實作差異、需求追溯方式，**只靠本文件即可查得**。
- 每張資料表的完整欄位級定義、每個 API 的完整 Request／Response、每張畫面的完整
  Wireframe 細節、每一條測試案例與操作步驟，由本文件摘要重要規則並**明確引用既有
  工程文件**（見 1.2 節），不全文複製，避免同一細節出現兩份權威版本。
- 被引用的工程文件若與本文件或 `docs/CURRENT_DECISIONS.md` 衝突，以本文件與
  `docs/CURRENT_DECISIONS.md` 記載的有效規格為準。

# 第 2 章 專案定位、目標與第一版範圍

## 2.1 平台定位

- **REQ-SCOPE-010**（MUST）〔角色：全部〕
  EchoGather 是《鳴潮》官方周邊的**開團資訊整合與跟團管理平台**，不是完整電商平台。
  平台 MUST NOT 處理實際金流、代收款、驗證付款、計算運費。
  - 驗收：全站無任何站內付款、對帳、退款、運費計算功能入口（07 §15、§22）
  〔來源：CD §2.1；01 §2〕
- **REQ-SCOPE-020**（MUST）〔角色：全部〕
  實際付款、補款與雙方聯絡透過平台外部工具（Facebook、Discord、LINE 等）進行；
  平台僅整合與呈現開團資訊、購物車（內部命名 `follow_list`，見章 23）與訂單狀態。
  - 驗收：訂單流程中無站內金流操作，聯絡資訊以快照與公開聯絡方式呈現（07 §18）
  〔來源：CD §2.1；01 §2〕

## 2.2 平台整合的資訊範圍

- **REQ-SCOPE-030**（SHOULD）〔角色：全部〕
  平台整合：官方活動、官方商品、商品關聯角色、多位團主的開團資訊（價格、付款方式、
  是否二補、是否包含滿贈、收單期限、團規、主要聯絡方式）、會員購物車、訂單狀態、
  團主公告（可選擇公開）與系統通知。
  - 驗收：上述每類資訊皆有對應章節與功能（章 5–13）
  〔來源：01 §2、§4；CD §2〕

## 2.3 第一版模組範圍

- **REQ-SCOPE-040**（MUST）〔角色：全部〕
  第一版包含模組：Authentication、User Profile、Group Leader Application、Activity、
  Product、Character、Group Buy、Follow List（UI 名稱「購物車」）、Order、
  Cancellation Request、Product Favorite、Announcement、Notification、
  Group Leader Dashboard、Administrator Dashboard、Image Upload、Global Search。
  - 驗收：模組與章 5–14 逐一對應；00 §3 模組對應表可追溯
  〔來源：01 §5；00 §3〕

## 2.4 第一版明確不提供

- **REQ-SCOPE-050**（MUST NOT）〔角色：全部〕
  第一版明確不提供的功能一律不得實作、不得於 UI 顯示入口；完整清單見章 20。
  代表性項目：站內付款／自動對帳／退款、二補金額管理、運費計算與物流追蹤、
  站內聊天與私訊、評價與星等、盲盒拆分與熱度定價、商品規格變體、多遊戲支援、
  行動 App、Refresh Token、帳號／團主資格／公告停用、會員自行刪除通知、
  開團草稿／排程發布／審核後發布、已結單開團重新開啟。
  - 驗收：章 20 清單全站無對應功能（07 §3.2）
  〔來源：CD §2.3、§15；01 §6〕

## 2.5 作品集目標（非功能性背景）

本專案同時作為個人作品集，展示 React 前端、FastAPI 後端、PostgreSQL 資料庫、
JWT 驗證、交易與鎖、權限管理、歷史快照等工程實務。此為背景說明，不構成產品需求。
〔來源：01 §4.6〕

# 第 3 章 使用者角色與權限總覽

## 3.1 角色定義

- **REQ-ROLE-010**（MUST）〔角色：全部〕
  系統包含四種使用者身分：
  | 角色 | 定位 |
  |---|---|
  | Visitor | 未登入使用者，只能瀏覽公開內容 |
  | Member | 已註冊並登入的使用者 |
  | Group Leader | **具備團主資格的會員**（具有 `group_leader_profile`），不是獨立帳號、不是獨立 `UserRole` 值 |
  | Admin | 獨立管理用途帳號（`app_user.role = admin`），只使用管理後台 |
  - 驗收：`UserRole` Enum 僅 `member`／`admin` 兩值（04 §5.1）；團主資格由是否具有團主資料判定
  〔來源：CD §2.2、§3.1；06 §3；04 §5.1〕

## 3.2 Visitor 權限

- **REQ-ROLE-020**（MUST）〔角色：Visitor〕
  Visitor 可以：瀏覽公開活動、商品、角色、開團比較、公開團規、已完成資料的團主公開頁、
  團主選擇公開的公告；使用全站搜尋；註冊；登入。
  Visitor MUST NOT：收藏、使用購物車、下單、提出取消申請、查看通知、申請團主、
  進入團主或管理員後台。
  - 例外／邊界：Visitor 嘗試使用會員功能時顯示需要登入提示並導向登入頁
  - 驗收：未帶 Token 呼叫受保護 API 回 401（07 §22；05 §32）
  〔來源：CD §3.1；06 §5.1；02 §3.1〕

## 3.3 Member 權限

- **REQ-ROLE-030**（MUST）〔角色：Member〕
  Member 除 Visitor 功能外，可以：管理個人資料與私人聯絡方式、收藏商品、使用購物車、
  送出訂單、查看自己的訂單、提出取消申請、查看與標記通知、申請團主資格。
  - 驗收：上述每項功能對應章 4–8、10、13 的 REQ；本人以外資源不可存取（章 15）
  〔來源：CD §3.1；06 §5.2〕

## 3.4 Group Leader 資格與權限

- **REQ-ROLE-040**（MUST）〔角色：Group Leader〕
  團主資格＝具有 `group_leader_profile` 的會員。團主擁有全部 Member 功能，
  另可於**公開資料完成後**（見 REQ-LEADER-050）：公開團主頁、建立與管理自己的開團、
  查看及處理自己開團的訂單（含會員聯絡快照）、處理取消申請、發布／修改／刪除自己的
  團主公告、查看團主 Dashboard。
  - 例外／邊界：公開資料未完成時，僅能進入團主資料設定頁（章 10）
  - 驗收：未完成資料時開團／公告 API 拒絕（07 §13；05 §32）
  〔來源：CD §2.2、§9.2；06 §3.3、§5.3；02 §3.3〕
- **REQ-ROLE-050**（MUST NOT）〔角色：Group Leader〕
  團主不得：管理其他團主的開團、查看其他團主的訂單或其會員聯絡方式、為其他團主
  發布公告、修改官方活動或商品、對**自己的開團**加入購物車或建立訂單（見 REQ-CART-080、REQ-ORDER-020）。
  - 驗收：跨團主資源操作回 404／403（05 §36.1；07 §22）
  〔來源：CD §3.1、§6、§7.1；06 §5.3、§5.5〕

## 3.5 Admin 帳號限制

- **REQ-ROLE-060**（MUST）〔角色：Admin〕〔狀態：待同步→D-06〕
  Admin 是獨立管理用途帳號，只使用管理後台（功能範圍見章 14）。
  Admin 帳號 MUST NOT 使用收藏、購物車、下單、團主申請與團主後台；
  Admin 不因管理員身分取得任何會員或團主功能。
  同一真人若需要會員或團主功能，MUST 使用另外的一般會員帳號；
  該一般會員帳號可與管理員帳號使用同一 Email（namespace 規則見 REQ-AUTH-040）。
  - 例外／邊界：無例外；此限制 MUST 由後端強制，不得只依靠前端隱藏入口
  - 驗收：Admin 帳號呼叫收藏／購物車／下單／團主申請／團主後台 API 一律拒絕（現況見 D-06）
  - 歷史說明：06 §3.5、01 §7.4 與 05 §32 權限矩陣曾記載「管理員另具團主資料時可使用
    團主功能」，該規則已被 CD §3.1 取代，一律不採用
  〔來源：CD §2.2、§3.1、§13.1〕

# 第 4 章 帳號、註冊、登入與個人資料

## 4.1 註冊

- **REQ-AUTH-010**（MUST）〔角色：Visitor〕
  註冊必須提供：Email、密碼、密碼確認、暱稱、以及 Facebook／Discord／LINE 至少一項
  私人聯絡方式。頭像為選填，未上傳時使用系統預設頭像。空白字串不視為有效聯絡方式
  （Trim 後為空轉為 `null`）。
  - 驗收：缺任一必填或三項聯絡全空時後端拒絕（05 §9.1；07 §12）
  〔來源：CD §3.2；06 §6.1；05 §9.1〕
- **REQ-AUTH-020**（MUST）〔角色：Visitor〕
  註冊必須通過 Email 驗證碼：6 位數、雜湊儲存、10 分鐘有效、單次使用；
  同一 Email 兩次寄送間隔至少 60 秒、每日上限 10 次、驗證碼錯誤 5 次後失效。
  **已註冊判定以一般用戶 namespace 為準**：一般用戶側已有該 Email 時不寄送；
  僅有 Admin 帳號使用同 Email 時仍可寄送並完成 Member 註冊
  （同一 namespace 內不得重複，REQ-AUTH-040）。
  - 驗收：各限制條件逐一觸發對應錯誤（07 §12）
  〔來源：CD §3.2〕
- **REQ-AUTH-030**（MUST）〔角色：Visitor〕
  註冊成功後**自動登入並導向首頁**；僅在自動登入失敗時，才導向登入頁並提示使用者登入。
  註冊時選擇的頭像於自動登入後上傳套用；頭像上傳失敗不影響帳號已建立的事實。
  - 例外／邊界：註冊 API 本身不簽發 Token，自動登入由前端以同組帳密呼叫登入 API 完成
  - 驗收：註冊成功後直接進入首頁且為登入狀態（07 §12；02 §8.5）
  〔來源：CD §3.2；06 §6.4；05 §9.1；02 §8.5〕

## 4.2 Email 與密碼

- **REQ-AUTH-040**（MUST）〔角色：全部〕〔狀態：已實作（migration
  `0014_admin_email_namespace`＋`auth_service.login` 唯讀驗證；Audit D-1）〕
  Email 儲存前 Trim、正規化為小寫、大小寫不敏感。
  **Email 唯一性依帳號 namespace（角色）分開計算**：一般用戶側同一 Email 最多
  一個帳號、管理員側同一 Email 最多一個帳號——因此同一 Email 可各建立一個
  Member 與一個 Admin 帳號，兩帳號的 ID、密碼、權限、資料與 Session 完全獨立；
  同一 namespace 內 MUST NOT 重複。
  登入時依 Email 取得候選帳號，再以密碼判斷登入哪一個帳號；兩帳號密碼皆相同時
  優先登入 Admin。**第一版會員不可自行修改 Email**（Admin 亦無修改入口）。
  - 例外／邊界：登入失敗訊息維持統一（REQ-AUTH-060），不因雙帳號而透露資訊
  - 歷史說明：原「全域不可重複」規則已依 2026-07-31 裁決（2026-08-04 收編確認）修訂
  - 驗收：同 Email 可建 Member＋Admin 各一、同側重複被拒；密碼決定登入帳號、
    同密碼登入 Admin（test_auth_api；07 §12）
  〔來源：CD §3.3（v1.2）；migration 0014〕

# 第 17 章 API Design 摘要

> 本章為規格層摘要。**逐端點完整 Request／Response 引用 `05_API_Design_v2.1`

> （如權限矩陣 Admin 欄、搜尋範圍）以本文件與 CD 為準。

## 17.1 基本慣例

- **REQ-API-010**（MUST）〔角色：系統〕
  Base URL `/api/v1`；JSON＋snake_case；UUID 以字串傳輸；時間 ISO 8601 UTC；
  金額以字串傳輸（Pydantic 解析為 Decimal）；Boolean 用 true／false；
  無資料用 `null`（不用空字串，聯絡方式空字串由後端轉 null）；
  圖片上傳用 `multipart/form-data`。
  - 驗收：回應格式抽查一致（05 §2；07 §22 API-004～005）
  〔來源：05 §2〕
- **REQ-API-020**（MUST）〔角色：系統〕
  資源命名用複數名詞（`/users/me`、`/group-leader/profile`、`/follow-list` 等
  單一資源例外）；GET 取得、POST 建立或明確狀態操作、PATCH 部分更新、
  DELETE 刪除允許刪除的資源。狀態變更 MUST NOT 以通用 `status` 欄位直接跳轉，
  MUST 使用明確 Action Endpoint（accept／reject／mark-paid／mark-shipped／
  complete／close／end／reopen／deactivate／reactivate）。
  - 驗收：無以 PATCH status 跳轉狀態之端點（05 §3.1–3.3；07 §22）
  〔來源：05 §3〕
- **REQ-API-030**（MUST）〔角色：系統〕
  回應格式：單一資源 `{"data": {...}}`；列表 `{"data": [...], "pagination": {...}}`
  （page、page_size、total_items、total_pages、has_previous、has_next）；
  操作成功回傳更新後資源；刪除可用 `204 No Content`。
  錯誤統一 `{"error": {"code", "message", "details"}}`；欄位錯誤 details 帶
  fields、狀態衝突帶 current_status、數量錯誤帶各項可接受數量。
  - 驗收：格式一致性測試（05 §5–6；07 §22）
  〔來源：05 §5–6〕
- **REQ-API-040**（MUST）〔角色：系統〕
  分頁統一 `page`／`page_size`（預設 1／20，上限 100；違反回 422）。
  預設排序 `created_at DESC`，例外：待審核團主申請 ASC、團主訂單處理列表
  `created_at ASC, id ASC`、開團比較預設新到舊。Query 未提供時不套用該篩選；
  傳入不存在的 Enum 值回 422。
  - 驗收：分頁排序篩選行為一致（05 §7；06 §28.7；07 §22）
  〔來源：05 §7；06 §28.7〕
- **REQ-API-050**（MUST）〔角色：系統〕
  冪等要求：重複收藏、取消不存在的收藏、通知標記已讀、全部已讀、清空不存在的
  購物車 MUST 冪等；重複上下架回目前狀態或 409。訂單、申請與數量等敏感操作
  以 409 Conflict 提示前端重新取得最新資料。
  - 驗收：重複呼叫不產生重複資料（05 §3.5；07 §22）
  〔來源：05 §3.5〕
