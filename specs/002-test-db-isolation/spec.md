# Feature Specification: 測試資料庫隔離（Test Database Isolation）

**Feature Branch**: `002-test-db-isolation`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "測試資料庫隔離：後端 pytest 測試目前直接使用 backend/.env 的 DATABASE_URL 連上主要 Supabase 資料庫，僅靠 transaction rollback 防止資料殘留。本功能新增 TEST_DATABASE_URL，測試一律改用它連到同一個 Supabase 專案內的獨立測試 schema（軟隔離）；未設定時測試直接中止；啟動時檢查不得指向主要 schema；建立獨立 test engine 與 session；保留 transaction rollback；測試 schema 以既有結構定義建立空的資料表；補安全測試；完成後完整 pytest 全數通過，網站正式運作完全不受影響。"

**權威來源**: `docs/CURRENT_DECISIONS.md` §14（測試與資料庫環境）第 1、2 條；
`docs/EchoGather_Product_Specification_v1.0.md` REQ-TEST-030、差異項 D-02（狀態：待同步）。
本功能完成後，D-02 由「待同步」轉為「已實作」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 測試與主要資料完全分流（Priority: P1）

開發者執行自動化測試時，所有測試產生的資料讀寫都發生在專用的測試資料區，
與網站實際使用的主要資料區完全分開。即使測試中途失敗、中斷或錯誤地寫入資料，
主要資料區的既有資料（活動、商品、會員、訂單等）也不會被建立、修改或刪除。

**Why this priority**: 這是本功能存在的理由。目前測試直接連主要資料區，
任何測試流程的失誤都可能污染或毀損網站正在使用的資料；
後續多項修正工作（D-06、D-14）都需要大量執行測試，必須先建立這道防線。

**Independent Test**: 記錄主要資料區的資料狀態後執行完整測試套件，
再次比對主要資料區——所有既有資料筆數與內容 MUST 完全不變；
測試期間的資料異動 MUST 只出現在測試專用資料區。

**Acceptance Scenarios**:

1. **Given** 測試環境已正確設定測試專用連線，**When** 執行完整測試套件，
   **Then** 全部測試通過，且主要資料區的任何資料表內容皆無增刪改。
2. **Given** 測試專用資料區已建立，**When** 單一測試於執行過程中寫入資料，
   **Then** 該筆資料只存在於測試專用資料區，且測試結束後被回滾清除。
3. **Given** 測試執行到一半被強制中斷，**When** 檢查主要資料區，
   **Then** 主要資料區無任何殘留的測試資料。

---

### User Story 2 - 設定錯誤時的安全防呆（Priority: P1）

開發者若尚未設定測試專用連線，或設定值錯誤地指向主要資料區，
測試框架在開始執行任何測試之前就直接中止，並以明確訊息說明原因與修正方式；
絕不退回使用主要資料區連線繼續執行。

**Why this priority**: 防呆是隔離的保證。沒有這層檢查，
新環境（重建 `.env`、新協作者、CI）第一次跑測試就可能直接打到主要資料區，
隔離機制形同虛設。

**Independent Test**: 分別在「未設定測試連線」與「測試連線指向主要資料區」
兩種錯誤情境下啟動測試，確認測試在執行任何案例前即中止並顯示對應錯誤訊息。

**Acceptance Scenarios**:

1. **Given** 未設定測試專用連線，**When** 啟動測試，
   **Then** 測試在執行任何案例前中止，錯誤訊息指出缺少測試連線設定，
   且不會退回使用主要資料區連線。
2. **Given** 測試專用連線設定值指向主要資料區（與主要連線相同、或未指定
   測試專用資料區），**When** 啟動測試，
   **Then** 測試在執行任何案例前中止，錯誤訊息指出測試連線不得指向主要資料區。
3. **Given** 上述任一錯誤情境，**When** 檢查主要資料區，
   **Then** 主要資料區無任何因啟動測試而產生的資料異動。

---

### User Story 3 - 測試資料區可重建且結構與主庫一致（Priority: P2）

開發者可以在測試專用資料區內，依既有的資料表結構定義，建立一套與主要資料區
結構相同、內容為空的資料表。此建置過程可重複執行（重建），
且完全不影響主要資料區的結構與資料。

**Why this priority**: 沒有結構一致的空資料表，測試無法在隔離環境中執行；
但它是 User Story 1 的支撐條件，故列於其後。

**Independent Test**: 對測試專用資料區執行結構建置後，
比對其資料表清單與主要資料區一致、內容為空；重複執行建置不產生錯誤；
主要資料區結構與資料在建置前後完全相同。

**Acceptance Scenarios**:

1. **Given** 測試專用資料區為空，**When** 執行結構建置，
   **Then** 測試專用資料區具有與主要資料區相同的資料表結構，且所有資料表為空。
2. **Given** 測試專用資料區已建置過，**When** 再次執行結構建置（重建），
   **Then** 建置成功完成，不留下舊測試資料。
3. **Given** 結構建置執行完成，**When** 檢查主要資料區，
   **Then** 主要資料區的結構與資料皆無任何變動。

---

### Edge Cases

- 測試連線設定存在但格式錯誤／無法連線：測試 MUST 在開始執行案例前以明確
  錯誤訊息中止，不得改用主要連線。
- 測試專用資料區存在但缺少部分資料表（結構過期）：受影響的測試以資料表不存在
  之類的錯誤失敗即可接受；MUST NOT 自動改連主要資料區取得結構。
- 主要資料區結構日後變更（新增 Migration）：測試專用資料區 MUST 可透過重新執行
  結構建置追上，無需人工逐表調整。
- 網站正式啟動（非測試）時：MUST 完全不讀取測試專用連線設定；
  未設定測試連線 MUST NOT 影響網站啟動與運作。
- 寄信攔截等既有測試防護：MUST 維持原有行為，不因本功能失效。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一個與主要資料連線設定分離的「測試專用資料連線設定」，
  測試執行時一律使用測試專用設定。〔來源：REQ-TEST-030 第 1 條；CD §14.1〕
- **FR-002**: 測試專用連線 MUST 指向與主要資料區分離的獨立測試資料區
  （本功能採同一資料庫服務內的獨立 schema 作為隔離單位）。
  〔來源：REQ-TEST-030 第 1 條〕
- **FR-003**: 未設定測試專用連線時，測試 MUST 在執行任何測試案例之前中止，
  並顯示指出缺少該設定的錯誤訊息；MUST NOT 退回使用主要資料連線。
  〔來源：REQ-TEST-030 第 2 條；CD §14.2〕
- **FR-004**: 測試啟動時 MUST 檢查測試專用連線不得指向主要資料區
  （包含：與主要連線指向同一資料區、或未指定測試專用資料區而落在預設主要區）；
  檢查不通過時 MUST 在執行任何測試案例之前中止並顯示對應錯誤訊息。
  〔來源：REQ-TEST-030 第 2 條；CD §14.2〕
- **FR-005**: 測試 MUST 使用獨立於正式運作的資料連線資源（獨立 engine 與 session），
  MUST NOT 與網站正式運作共用同一連線資源。
- **FR-006**: 每個測試案例 MUST 維持既有的交易回滾機制：
  測試中寫入的資料於該測試結束後 MUST 被回滾，不殘留於測試資料區。
- **FR-007**: 系統 MUST 提供可重複執行的測試資料區結構建置方式，
  依既有結構定義在測試資料區建立與主要資料區相同、內容為空的資料表；
  建置過程 MUST NOT 對主要資料區進行任何結構或資料變更。
- **FR-008**: 系統 MUST 包含驗證防呆行為本身的安全測試：
  涵蓋「未設定測試連線」與「測試連線指向主要資料區」兩種情境皆被拒絕。
- **FR-009**: 網站正式運作 MUST 完全不受本功能影響：
  主要連線設定的用途、內容與行為皆不變；測試專用設定未存在時網站照常運作。
- **FR-010**: 既有測試防護（寄信攔截等外部副作用攔截）MUST 維持原有效果。
  〔來源：REQ-TEST-030 第 5 條；CD §14.5〕

### Key Entities

- **主要資料連線設定（DATABASE_URL）**: 網站正式運作使用的資料庫連線，
  指向主要資料區（現況 public schema）。本功能 MUST NOT 變更其內容與用途。
- **測試專用資料連線設定（TEST_DATABASE_URL）**: 僅供自動化測試使用的連線，
  指向測試專用資料區。與主要設定分離存放，未設定時測試中止。
- **測試專用資料區（測試 schema）**: 同一資料庫服務內、與主要資料區分離的
  獨立區域，結構與主要資料區一致、平時為空，可重建。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 執行完整測試套件前後，主要資料區所有資料表的筆數與內容 100% 不變。
- **SC-002**: 在未設定測試連線與測試連線指向主要資料區兩種錯誤情境下，
  被實際執行的測試案例數為 0，且皆顯示可辨識原因的錯誤訊息。
- **SC-003**: 隔離機制完成後，完整測試套件通過率與功能改動前相同
  （既有通過的測試 100% 仍通過）。
- **SC-004**: 開發者依文件在乾淨環境（重建 `.env`）完成測試環境設定並成功
  跑完測試，所需人工步驟不超過 2 步（填入測試連線設定、執行結構建置）。
- **SC-005**: 網站正式功能於本功能完成後行為不變（不需任何前端或 API 行為驗證
  以外的改動；主要連線相關程式路徑無行為差異）。

## Assumptions

- 依專案負責人 2026-08-04 裁決，隔離單位採「同一 Supabase 專案內的獨立
  PostgreSQL schema」（CD §14.1 允許的三種方式之一），屬軟隔離：
  測試與正式共用同一資料庫角色，靠連線層的資料區指定與啟動防呆分流；
  日後如需硬隔離（獨立專案或本機資料庫），僅需更換測試連線設定值，
  防呆機制與測試流程不需重做。
- 測試專用設定命名沿用使用者指定的 `TEST_DATABASE_URL`，
  存放位置與主要設定相同（`backend/.env`，已於 .gitignore 排除）。
- 測試資料區的結構以程式中既有的資料表結構定義建立（空資料），
  不複製主要資料區的任何資料；測試所需資料一律由測試自行建立。
- 現行連線方式（Session pooler）支援指定資料區的連線參數；
  實作時以實際連線驗證，若不支援則回報並改由直連連線埠處理，不影響本規格內容。
- 本功能為純後端測試基礎建設，無任何使用者介面變更，
  故不適用前台改版「先列差異、等判定」流程；但仍遵循「未經同意不 commit」慣例。
- 平行測試（多 worker 同時執行）非本功能範圍；本功能只需保證單一測試流程的隔離，
  不因此排除日後擴充。
