# EchoGather Constitution

EchoGather｜鳴潮周邊團購平台（程式碼倉庫名 `WuWaGroup`）的長期治理原則。
本文件規範「規格文件如何被建立、維護與驗證」，不規範個別產品或業務細節。
個別產品與業務決策由 `docs/CURRENT_DECISIONS.md` 與後續正式規格文件管理。

## Core Principles

### I. Brownfield 專案保護

EchoGather 是已上線運行的既有專案。導入 Spec Kit 的目的是整理既有事實，不是重新設計。

- 任何規格整理或文件修改，MUST 先閱讀相關的既有文件、程式碼與測試後才動筆。
- MUST NOT 將本專案視為空白專案重新設計架構、資料模型、流程或介面。
- MUST NOT 因為整理文件而重寫、重構或修改既有功能程式碼、測試或 Migration。
- 工作過程中發現、但與本次文件範圍無關的問題，MUST 記錄為待辦或差異項，
  MUST NOT 順手處理。
- 文件整理工作 MUST NOT 附帶執行測試、Migration、資料庫操作、套件安裝或部署；
  確有需要時 MUST 另行提出並取得專案負責人同意。

**可檢查方式**：本次工作的實際變更檔案清單，MUST 完全落在事前宣告的允許修改範圍內；
變更清單中出現任何未宣告的產品程式碼、測試或 Migration，即為違反本原則。

### II. 需求與文件權威順序

- `docs/CURRENT_DECISIONS.md` MUST 作為目前有效產品與業務決策的主要權威來源。
- 後續建立的正式規格文件 MUST 與 `docs/CURRENT_DECISIONS.md` 一致。
- 舊文件與最新決策衝突時，MUST 在文件中明確標示衝突點與來源，並以最新決策為準；
  MUST NOT 以舊文件內容覆蓋最新決策。
- 程式碼或測試中已實作的行為，MUST NOT 因為「已經做出來了」而自動取得正式需求地位；
  取得正式需求地位 MUST 有對應的決策來源。
- MUST NOT 自行補充、推測或擴充未經確認的產品規則。

**可檢查方式**：任一條正式需求，MUST 能指出其權威來源（最新決策章節編號或後續正式
規格條號）；指不出來源的敘述 MUST 從正式需求中移除，或改列為待確認事項。

### III. 正式規格完整性

正式規格文件體系 MUST 清楚涵蓋下列面向，缺一即視為規格不完整：

- 專案定位與範圍
- 角色與權限
- 功能需求
- 業務規則
- 使用者流程
- UI 與畫面狀態
- Database Design
- API Design
- 測試與驗收條件
- 已知規格與實作差異

每一條重要需求 MUST 滿足：

- 使用明確且可檢查的文字，並以 MUST／MUST NOT／SHOULD 標示強度。
- 區分正常流程、例外情形、權限限制與邊界條件。
- 具有可追溯的驗收方式（可對應到驗收條件或測試情境）。
- MUST NOT 使用「通常」「可能」「視情況」「盡量」等無法判定的模糊措辭。

**可檢查方式**：對任一條重要需求提問「要怎麼判定它有沒有被滿足？」，MUST 能在文件內
找到明確答案；答不出來即為不合格需求。

### IV. 衝突與不確定事項處理

- 發現文件、程式碼與測試三者之間不一致時，MUST 逐項列出來源位置與具體差異內容，
  MUST NOT 只做籠統描述。
- MUST NOT 未經專案負責人確認就自行裁決產品需求；遇到需要裁決的問題 MUST 提出詢問。
- 已確認但程式尚未同步的內容，MUST 標記為「已知規格與實作差異」，
  MUST NOT 混入待確認事項。
- 尚未確認的內容 MUST 與正式需求分開存放，MUST NOT 在實作時當作已確認規格使用。
- 維運待辦、部署事項、測試執行紀錄與產品業務規則，MUST 分開管理，MUST NOT 互相混寫。

**可檢查方式**：任一份規格文件中，「已確認需求」「已知差異」「待確認事項」三類內容
MUST 位於彼此分離且標題明確的章節；三類內容出現在同一段落即為違反。

### V. 規格與實作分離

- 正式規格描述「系統應有的行為」；現有實作狀況描述「系統目前做到的程度」。
  兩者 MUST 分開敘述。
- 「已確認」「已實作」「待同步」「延後」「待確認」等狀態 MUST 依本文件
  〈正式規格文件體系與狀態詞彙〉的定義使用，並清楚標示於對應項目。
- MUST NOT 因為目前程式尚未同步，就降低、刪除或改寫已確認的需求。
- MUST NOT 因為規格已確認，就宣稱程式已完成。

**可檢查方式**：文件中任一被描述為「已完成」的項目，MUST 有明確的實作狀態依據；
任一被描述為「規格如此」的項目，MUST 有明確的決策來源依據；兩者 MUST NOT 互相代替。

### VI. 範圍與變更控制

- 每一次文件整理工作 MUST 在開始前宣告明確的修改範圍（允許修改與禁止修改的檔案）。
- MUST NOT 在同一次工作中順便修改與宣告範圍無關的文件或程式碼。
- 大型規格整理 SHOULD 分階段完成，每一階段結束時逐步檢查，而非一次產出全部文件。
- 任何正式規格變更 MUST 同步更新該文件的版本號、最後更新日期與受影響章節。
- 已被撤回或被取代的規則，MUST 保留必要的歷史說明與失效標記，
  MUST NOT 直接刪除到無跡可循，以免日後再次被誤用。

**可檢查方式**：每次工作結束時，實際變更檔案清單 MUST 可逐一對應到事前宣告的範圍；
每份被修改的正式規格文件，其版本與日期欄位 MUST 已更新。

### VII. 文件可追溯性

正式需求 SHOULD 能追溯至下列各項（適用者為限）：

- 最新決策來源
- 對應使用者流程
- UI 規格
- API 規格
- Database Design
- 業務規則
- 驗收條件
- 目前實作差異

用語一致性規則：

- 不同文件 MUST NOT 以不同名稱描述同一個使用者概念。
- 唯一例外為明確區分「使用者介面名稱」與「內部技術名稱」，
  且該區分 MUST 在文件中被明確說明，並註明其為已確認狀態或待處理差異。

**可檢查方式**：抽查任一條正式需求，MUST 能沿追溯鏈找到其決策來源與驗收方式；
抽查任一使用者概念，其在各份文件中的名稱 MUST 一致，或有明確的名稱對照說明。

### VIII. 誠實報告與品質檢查

- 未實際閱讀的內容，MUST NOT 宣稱已完整檢查。
- 未實際執行的測試，MUST NOT 宣稱已通過或已驗證。
- 無法判定的內容 MUST 明確標示為無法判定，並說明原因，MUST NOT 以推測填補。
- 完成任一份正式規格文件前，MUST 進行跨文件一致性檢查。
- 交付的文件中 MUST NOT 留下未填的 placeholder、互相矛盾的規則，或已失效的需求。
- 可選的改善建議 MUST NOT 被描述成必要缺陷或系統錯誤。

**可檢查方式**：完成報告中的每一項「已檢查」「已通過」宣稱，MUST 對應到實際執行過的
閱讀或指令；交付文件全文搜尋 MUST 找不到殘留的方括號佔位符或 TODO 標記。

## 正式規格文件體系與狀態詞彙

### 文件分層

| 層級 | 內容 | 目前對應檔案 |
|---|---|---|
| 治理層 | 跨文件、跨功能的長期原則 | `.specify/memory/constitution.md`（本文件） |
| 決策層 | 目前有效的產品與業務決策（權威來源） | `docs/CURRENT_DECISIONS.md` |
| 規格層 | 正式規格文件與需求追蹤 | `docs/00_Requirements_Traceability_Matrix.md`、`docs/01_Project_Specification_v2.1.md`、`docs/02_User_Flow_v2.1.md`、`docs/03_UI_Wireframe_Specification_v2.1.md`、`docs/04_Database_Design_v2.1.md`、`docs/05_API_Design_v2.1.md`、`docs/06_Business_Rules_v1.0.md`、`docs/07_Testing_and_Acceptance_Plan_v1.0.md`，以及後續 `specs/` 下的 Feature Spec |
| 紀錄層 | 進度、測試執行紀錄、部署與維運資訊 | `docs/目前進度.txt`、`docs/測試結果.md`、`docs/部署指南.md` |

規則：

- 決策層與規格層衝突時，MUST 以決策層為準（原則 II）。
- 紀錄層 MUST NOT 被當作產品需求來源引用（原則 IV）。
- 規格層文件 MUST NOT 默默覆蓋治理層原則（原則九）。
- 涉及執行測試、Migration 或資料庫操作時，MUST 遵循 `docs/CURRENT_DECISIONS.md`
  第 14 節〈測試與資料庫環境〉的規定；本文件不重複記載其細節。

### 狀態詞彙定義

| 狀態 | 定義 | 可否作為實作依據 |
|---|---|---|
| 已確認 | 已由專案負責人裁決的產品或業務規則 | 可 |
| 已實作 | 程式碼與測試已達成該已確認規格 | 可 |
| 待同步 | 規格已確認，但程式尚未跟上，屬已知規格與實作差異 | 規格可，現況描述 MUST 註明尚未實作 |
| 延後 | 已確認不屬於目前版本範圍 | 不可 |
| 待確認 | 尚未取得明確裁決 | 不可 |

這五個詞彙 MUST 在所有正式規格文件中維持同一定義；
MUST NOT 在個別文件中另行賦予不同含義。

## 文件整理工作流程與品質門檻

每一次規格整理工作 MUST 依序完成下列步驟，任一步驟未完成 MUST NOT 宣告工作完成：

1. **宣告範圍**：列出本次允許修改與禁止修改的檔案，以及禁止執行的操作（原則 VI）。
2. **閱讀來源**：實際讀取相關的決策文件、舊規格文件、程式碼與測試（原則 I、VIII）。
3. **比對差異**：列出文件、程式碼與測試之間的不一致，標明來源位置（原則 IV）。
4. **分類歸檔**：將內容分為已確認需求、已知規格與實作差異、待確認事項三類（原則 IV、V）。
5. **撰寫規格**：依原則 III 的完整性與明確性要求撰寫，並建立追溯關係（原則 VII）。
6. **一致性檢查**：跨文件檢查用語、狀態標記與需求編號是否一致（原則 VII、VIII）。
7. **誠實回報**：僅回報實際完成的項目，明確列出無法判定與需人工確認的事項（原則 VIII）。

品質門檻（Quality Gates）——交付前 MUST 全部通過：

- 無殘留 placeholder、方括號佔位符或未解決的 TODO。
- 無互相矛盾的規則，或矛盾已被明確標示為已知差異並註明處理方式。
- 每條重要需求皆具備明確強度用詞與可驗收的判定方式。
- 已確認需求、已知差異、待確認事項三類內容分區存放且標題明確。
- 本次變更範圍與事前宣告一致，未夾帶無關修改。

`/speckit-plan` 的 Constitution Check 於執行時讀取本文件，並以上述原則與品質門檻
作為 Gate 判定依據。

## Governance

本節即原則九〈治理〉。

**適用範圍**

- 本 Constitution 是跨文件、跨功能的長期治理原則，規範規格文件的建立與維護方式。
- 產品與業務細節 MUST 由 `docs/CURRENT_DECISIONS.md` 與正式規格文件管理，
  MUST NOT 寫入本文件。單一產品細節（例如個別功能的搜尋範圍、付款方式選項、
  特定按鈕名稱、欄位長度與畫面尺寸）MUST NOT 出現在本文件中。
- 較低層級文件 MUST NOT 默默覆蓋本 Constitution；如確有需要偏離，
  MUST 於該文件中明確標示偏離項目與理由，並提報修訂本 Constitution。
- 本 Constitution MUST NOT 被解讀為要求現有專案重新開發或重新設計。

**修訂程序**

- 修改本 Constitution MUST 說明：修改原因、影響範圍（受影響的原則與文件）、
  以及版本變化。
- 修改 MUST 同步更新文末的版本號與 Last Amended 日期，並於檔案頂端的
  Sync Impact Report 記錄變更內容。
- 修改後 MUST 檢查 `.specify/templates/` 下的模板是否仍與本文件相容；
  僅在確實不相容時才修改模板，MUST NOT 為了製造變更而修改已相容的模板。

**版本政策（Semantic Versioning）**

| 變更類型 | 版本位階 |
|---|---|
| 重大治理原則變更：移除原則、重新定義原則造成向後不相容 | MAJOR |
| 新增原則，或實質擴充既有原則的規範內容 | MINOR |
| 文字澄清、錯字修正、格式調整等非語意變更 | PATCH |

**合規檢查**

- 每次規格整理工作完成時，MUST 對照〈文件整理工作流程與品質門檻〉自我檢查。
- 發現既有文件違反本 Constitution 時，MUST 記錄為待處理項目，
  MUST NOT 在無關的工作中順手修改（原則 I、VI）。
